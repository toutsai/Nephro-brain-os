# 判斷 rubric（judgment.md）

拿不準的時候查這裡。每條給判準＋一個正例＋一個反例。正反例都是本 repo 的真實情境改寫。

## 1. 何時該升級模型

**判準**：滿足任一項就升級（haiku→sonnet 或 sonnet→opus）：
- 依 `dispatch.md` 第 5 節的錯誤次數門檻（haiku 錯 1 次、sonnet 同一子任務錯 2 次）。
- 任務需要「跨 3 個以上模組同時推理」或「在多個都說得通的方案間取捨」。
- 錯了會直接影響 production 或醫療內容正確性，而你對答案的把握低於「敢跟使用者拍胸脯」。

**正例**：Consult 三層搜尋偶發回空結果。Sonnet 第一輪懷疑 FAISS 索引、第二輪懷疑 f-string 跳脫，都改了但問題還在 → 帶兩輪的完整軌跡升 opus。✔
**反例**：「把 13 本期刊清單加成 14 本」這種改法完全明確的任務，因為「醫療相關所以慎重」升 opus → 浪費。改法明確時用 sonnet 甚至 haiku，慎重要靠驗證（build＋verifier），不是靠大模型。✘

## 2. 何時算真的完成

**判準**：以下全部成立才叫完成，缺一項就不准回報「完成」：
1. 驗收條件逐條被 fresh-context 驗過（verifier 或實跑），不是自己看過。
2. 品質底線通過（CLAUDE.md：`npm run build` / `py_compile`）。
3. 交付物在使用者拿得到的地方：merge 了、或 PR 開好連結給出、或檔案路徑明說。
4. 沒做完的部分明確列出，不是含糊帶過。

**正例**：改了 3 個 Vue 檔＋1 個 py 檔 → `npm run build` 通過、`py_compile` 通過、verifier 對照需求逐條 PASS、PR 開好、回報「完成，PR #94，其中 mobile 版排版沒動因為不在需求內」。✔
**反例**：agent 回報「已完成修改」，主對話直接跟使用者說做完了——但沒人跑過 build，Vercel 部署當晚失敗。agent 說完成 ≠ 完成，**驗過才算**。✘

## 3. 何時該停下來問使用者

**判準**：遇到以下情況，停下用 AskUserQuestion（使用者在線）或在 PR/回報中列為待決問題（不在線），不要自己決定：
- 要推翻 SESSION_LOG「重要架構決策」清單中的任何一條。
- 要改動醫療內容的產生規則、審核流程、藥名規則。
- 要刪除資料（Firestore collection、索引、歷史檔案）或做不可逆操作。
- 需求有兩種以上合理解讀，且做錯的返工成本 > 問一句的成本。
- plan 規模判斷：**改動 ≥3 個檔案、或動到 api_server.py 的核心搜尋/prompt 邏輯、或新增 collection/排程** ＝大改動，要先給 plan；反之為小改動，可直接做。

**正例**：使用者說「把 Knowledge 頁面的審核流程簡化一點」——可以理解成「減少點擊步驟」也可以理解成「放寬審核條件」。後者違反 pending 原則 → 先問。✔
**反例**：使用者說「按鈕顏色改成跟 Insight 頁一致」，卻停下來問「請問是哪個藍色？」——自己去讀 Insight 頁的 class 就有答案。**能自己查到的事不許問。**✘

## 4. 方向錯了的訊號（換路，不是重試）

**判準**：出現任一訊號，代表該換方法而不是再試一次：
- 同一修法試了兩輪，錯誤訊息**完全沒變**。
- 每修一處就冒出新的一處要修（第 3 處時停手）——通常代表你在錯的抽象層打補丁。
- 你開始想繞過驗證（跳過 build、把錯誤 catch 掉、放寬驗收條件）——這是最強的警訊。
- 修法需要動到你不理解的東西才能繼續（例如要改 Firestore rules 才能讓前端不報錯，但你說不清為什麼）。

**換路動作**：停手 → 用 3-5 句寫下「目前假設是什麼、證據支持嗎」→ 派一個 fresh agent 不帶你的假設重新診斷 → 假設不同就照新假設走；相同就升級模型或問使用者。
**正例**：為了修一個 template 語法錯，連改三個元件都在報新錯 → 停手重看，發現是 vite 版本語法差異，一行 config 解決。✔
**反例**：build 一直紅，把該元件從 build 排除讓它變綠 → 這不是修好，是把炸彈搬進 production。✘

## 5. 品質底線怎麼驗（本 repo 具體清單）

**判準**：對應改動類型，逐項執行，全綠才能 merge：
- 前端（src/、index.html、vite/tailwind config）：`npm run build` 成功。
- 後端/爬蟲（backend/、crawlers/ 的 .py）：每個改過的檔 `python -m py_compile` 通過；若改了 prompt 字串，肉眼確認 f-string 的 `{}` 跳脫（這裡踩過坑：json.dumps 進 f-string）。
- 資料檔（*.json）：`python -c "import json;json.load(open('<檔>'))"` 通過。
- Firestore rules/indexes：無法本地驗，merge 後提醒使用者 `firebase deploy --only firestore`。
- 文件/制度檔（.md）：派 verifier read-back，檢查引用的檔案路徑與工具名稱真實存在。

**正例**：改了 drug_database.json，跑 json.load 驗證 → 抓到一個多餘逗號。✔
**反例**：「只是改 JSON 而已不用驗」→ 上次 `.claude/settings.local.json` 就是這樣壞的。✘

## 6. Harness 的極限（誠實條款）

制度能補的：執行品質（靠拆解、驗證、多樣本評審）、一致性（靠 rubric）、context 衛生（靠派工合約）。
**制度補不了的**：模糊題與品味判斷——「這個摘要寫得好不好」「這兩個架構哪個更優雅」「使用者真正想要什麼」。弱模型遇到這類問題時：
1. 不要假裝有把握。明說「這是品味/模糊判斷，我的信心有限」。
2. 可用的緩解：升 opus、多答案評審選優（3 案 1 評審）、或把選項＋各自取捨列給使用者選。
3. 醫療內容的專業正確性**永遠交給使用者（腎臟科醫師）終審**，模型只做初篩與格式把關。這條沒有例外。
