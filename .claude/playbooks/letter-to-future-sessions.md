# 給未來 session 的信

寫於 2026-07-06，由 Claude Fable 5（使用者唯一一次用它的機會）。這封信給之後在這個環境工作的每一個模型——多半是 Sonnet，有時是 Haiku 或 Opus。你不需要比我強才能做好這份工作；你需要的是照制度走，並且誠實。

## 使用者沒問、但你必須知道的三件事

### 1. 這個系統的最大風險不是 code 寫壞，是「靜默腐敗」

這是一個單人維護的醫療知識系統：爬蟲每週自動跑、AI 自動摘要、自動連結概念。沒有測試套件、沒有 staging、main 直通 production。錯的 code 會在 build 時炸掉（看得見）；但**錯的資料不會**——一個爬蟲 prompt 被改壞、一個藥名被翻成中文、一筆 synthesis 繞過 pending 直接生效，可能幾週後才被發現，而使用者是拿這些內容做臨床參考的腎臟科醫師。
所以：任何動到「資料產生路徑」（crawlers/ 的 prompt、api_server.py 的 prompt、審核 status 邏輯）的改動，風險等級都比它的 diff 大小高一級。改這些時：diff 再小也要给使用者看過、改完抽查實際產出的資料（跑一筆看輸出），不要只看 code。

### 2. 「merge 了」和「活著」之間有三個斷層

這個環境有三個容易忘的部署/生效斷層，SESSION_LOG 待辦區就是為它們存在的：
- **後端**：merge ≠ 部署。只有使用者本機能跑 `gcloud run deploy`。你能做的是把提醒寫進 session 結尾與 SESSION_LOG。
- **Firestore rules/indexes**：同上，需要使用者跑 `firebase deploy --only firestore`。索引沒部署時查詢會直接報錯，症狀看起來像 code bug——先查這個再 debug。
- **GitHub Actions 排程**：寫好了 ≠ 有在跑。排程可能因為 secrets 過期、API 額度、上游格式改變而靜默失敗。如果使用者抱怨「最近都沒新文章」，第一步是去看 Actions 執行紀錄，不是讀爬蟲 code。

### 3. 使用者是醫師，不是工程師——他給的是臨床需求，不是規格

需求常是「Consult 的回答再準一點」「這頁用起來卡」。不要逐字翻譯成第一個想到的技術方案。先把你的解讀翻譯回去：「我理解成 X，打算改 Y，預期效果 Z」，一句話確認再動手。他在線時回覆很快，問一句的成本遠低於做錯一輪。反過來，工程內部決策（怎麼拆檔案、變數命名、用哪個 API 呼叫方式）不要拿去煩他——那是你的工作。

## 這套制度最可能的退化方式與預防

1. **SESSION_LOG 再次肥大**。誘因永遠存在：「這條很重要，先留著」。預防：80 行是硬上限，收尾時跑 `wc -l .claude/SESSION_LOG.md` 檢查；「重要」的東西該去的地方是 archive（歷史）、教訓區（規則）或 CLAUDE.md（硬規則），不是 log。
2. **派工變成儀式**。退化的樣子：模板照貼但驗收條件寫「確保正確運作」這種空話、verifier 派了但 FAIL 被無視、回報合約不符也照收。預防：驗收條件必須是**可判定的**（有檔名、有指令、有預期輸出）；verifier 回 FAIL 而你想直接跳過時，那就是 judgment.md 第 4 條的「想繞過驗證」警訊。
3. **規則被逐次豁免蛀空**。「這次情況特殊，先 merge 再說」發生三次，規則就死了。預防：豁免可以，但每次豁免必須在 SESSION_LOG 留一行記錄（豁免了什麼、為什麼）；同一條規則被豁免兩次＝規則可能不合理，走 maintenance.md 問使用者改規則，而不是繼續默默繞過。
4. **playbooks 與現實脫節**。工具名、agent 型號、指令會變；引用失效的規則會讓弱模型整段忽略該檔案。預防：發現任何一處失效，當場修（這屬於 maintenance.md 的「明確事實錯誤，可自行改」），不要「下次再說」。
